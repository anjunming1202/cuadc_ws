# docs/spec/

我们自己的设计规范——架构、模块划分、接口约定。跟 `docs/reference/`
（外部权威来源摘录）不同，这里的内容因为我们自己的设计迭代而改，不是
因为外部规则变了才改。

## 文档角色划分

目前只有一份正式 spec 文档——**`00-index.md`**，范围声明、模块划分、
数据流、任务状态机、接口约定、安全等内容都按章节写在里面。这是刻意的：
在某个模块的内容还没多到需要独立维护之前，不预先建一堆空占位文件。

当 `00-index.md` 里的某个章节（比如某个模块的详细设计）写得足够长、
或者变化频率明显和其它章节不一样、开始影响阅读和协作时，才把那一节
拆成独立文件，从 `00-index.md` 对应位置链接过去。拆出去的文件用两位
数字前缀递增编号（比如 `01-interfaces.md`），数字只表示"从主文档拆分
出来的顺序"，不是提前规划好的固定目录——具体拆成几份、什么时候拆，
由内容自然决定。

## ADR（架构决策记录）

放在 `docs/spec/adr/`，文件名格式 `NNNN-slug.md`（四位数字前缀递增编号）。

- 一个决策一份文件，写定后**不回改正文**。
- 如果决策后来变了，新开一份 ADR，在新文件里说明取代关系（例如
  "Supersedes 0001"），不删除或改写旧 ADR——旧 ADR 仍然真实记录了
  "当时为什么这么决定"。
- 只有确实做出决策的事项才写 ADR；还在讨论、没有拍板的开放问题不写
  ADR（也不写进 `00-index.md` 等正式 spec），继续留在讨论记录里。

## 决策权责

架构和技术决策由人决定（讨论中通过确认或提问达成一致后拍板）；AI
负责把已经达成一致的决策写成正式的 spec/ADR 文档——这与仓库
`CLAUDE.md` 里"人：系统设计、架构、技术决策；AI：实现、算法、文档"
的分工一致。不确定、还没拍板的架构判断不写进 `docs/spec/` 的正式文档。
