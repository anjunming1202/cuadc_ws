# Working notes — pre-spec discussion (2026-07-06 ~ 2026-07-07)

> **本文件性质**：不是正式 spec。是"讨论到这里，已经决定了什么、还有什么
> 没决定"的交接记录，供在 WSL 上继续设计讨论时做起点，避免重新推导一遍。
> 内容一旦被整理进正式的 `docs/spec/*.md`，对应部分应从本文件删除——本文件
> 应该只是过渡态，不应该和正式 spec 长期并存、变成第二个事实来源。

## 已经决定的事

- **范围**：本仓库只覆盖伴随计算机软件（感知/视觉、规划/决策、与
  ArduPilot 的通信接口）。飞控本身（Pixhawk 参数、PID、机体、投放机构）
  由飞控组负责，不在本仓库范围内，只作为外部接口契约引用（见
  `docs/reference/ardupilot-interface-overview.md`）。
- **ROS 版本**：ROS2 Humble（与本机其它项目 `ros_ws` 环境一致，已安装在
  `/opt/ros/humble`）。
- **仓库布局**：仓库根目录本身就是 colcon workspace 根（`src/` 直接在根下，
  不额外嵌套一层），docs/spec 是设计规范、docs/reference 是外部背景资料，
  两者更新的动机不同（spec 因为我们自己设计变了而改，reference 只因为外部
  来源变了或摘录有误才改）。
- **git**：单一仓库（docs 和代码放一起，不拆成两个仓库），因为 spec 变化
  和代码实现紧密相关，希望同一个 commit/PR 里能同时看到两者的对应关系。
- **仿真资产归属**：
  - 我们自己写的仿真场景（比赛场地世界文件、天井/靶标模型、spawn 和话题
    桥接的 launch 文件）属于我们自己的代码，应该是 `src/` 里的一个普通
    ROS2 包（暂定名 `cuadc_sim`，未最终确定）。
  - **ArduPilot SITL**（ArduPilot 固件自带的软件在环模拟器）和
    **`ardupilot_gazebo`**（连接 SITL 飞行动力学和 Gazebo 物理/传感器的
    桥接插件）都是第三方代码，不是我们写的，**不 vendor 进本仓库**，应作为
    外部依赖单独安装（类似 ROS2 Humble 本身不会被塞进任何项目仓库）。
  - 仿真器具体选型（Gazebo 还是别的）**还没有正式拍板**，Gazebo 只是因为
    ArduPilot 官方有现成的 `ardupilot_gazebo` 桥接插件而被提及，值得注意
    的是：如果选了一个和 ROS2 不兼容的仿真器（比如 Webots），会被迫出现
    类似 `~/projects/OxbotsSimulator` 那种顶层结构分裂（仿真器原生目录
    约定 vs ROS2 的 colcon 约定互不兼容，只能分开摆或者互相嵌套）。
- **外部时间约束**：飞控组 phase 1（人工控制下让飞机飞起来、按软件组给出
  的模拟指令调试控制器）需要在 **2026-08-01 前**完成，这依赖软件组尽早
  定下确定的指令接口格式（轨迹/模式/速度输出的数据类型）。这是设计
  规划/决策模块对外接口时，应该优先跑通的部分，而不是留到最后。

## 还没决定、需要讨论的开放问题

1. **接口层要不要独立成一个模块/包**：ArduPilot/MAVLink 通信细节（订阅
   telemetry、发送 GUIDED 指令等）是单独一个模块（比如 `mavros_bridge`，
   和"规划/决策"的决策逻辑分开），还是直接算在规划/决策模块内部？倾向于
   分开（决策逻辑可以脱离真实/仿真飞控单独测试），但没有最终拍板，需要
   讨论。
2. **`docs/spec/00-index.md`（顶层架构/索引文档）还没写**，有一个提案大纲
   （见下），需要讨论确认后再动笔：
   1. 一句话范围声明（伴随计算机软件，飞控/机体/电源/投放机构是外部契约）
   2. 模块划分（感知/视觉、规划/决策、[接口层？]、日志）
   3. 顶层数据流图（相机 → 感知 → 目标信息 → 规划决策 → 接口层 →
      ArduPilot GUIDED → 遥测回传 → 规划决策）
   4. 任务状态机粗粒度阶段（起飞 → 搜索/侦察 → 目标选择 → 打击 → 返航），
      细节留给 `03-planning.md`
   5. 模块清单 + 各自文档链接（指向 `01-conventions.md`、`02-perception.md`、
      `03-planning.md`、`04-interfaces.md`、`05-safety.md`，即使这些文件
      现在还不存在）
   6. 明确写"非目标"：不覆盖飞控内部调参、机体结构、电源、投放机构机械
      设计
3. **附件12 图片靶标顺序未核对**：12 页轮廓图和目标价值表的一一对应关系
   没有验证过（见 `docs/reference/target-classes.md` 里的提示），实现
   感知模块前需要人工核对一次。
4. **"中位数"打击规则里 3 个数字相同时怎么处理**：规则原文没写，需要向
   裁判组确认或自己定一个保守假设（见 `docs/reference/target-classes.md`）。
5. **仿真到底要搭多真**：ArduPilot SITL 本身不需要 Gazebo 就能测规划/
   决策/控制逻辑（自带简化飞行动力学），感知模块用合成图片/录制视频测试
   可能比搭一个逼真 3D 场景更快出结果——"要不要接完整的 Gazebo 视觉仿真"
   和"规划决策逻辑仿真"可以分开决定，值得在某个模块文档（可能是感知模块
   文档或者专门的"开发与仿真环境"文档）里详细讨论，现在不用决定。

## 早期架构草案里可复用的部分（已按现在的范围重新解读）

早期有一份 `CUADC项目框架（初步方案）.md`（Windows 侧
`/mnt/e/ajm Projects/CUADC 2026/`，WSL 可通过 `/mnt/e/...` 直接访问），
写于**知道具体比赛规则之前**，范围也比现在宽（还包含飞控/电源/机体/投放
机构等现在明确不归我们管的内容）。**不要把原文整份拿来当参考**——下面是
已经按"仅伴随计算机软件"的范围 + 已知的具体比赛规则重新过滤/解读过的
可复用部分，原文本身不需要再迁移或保留第二份。

**感知/视觉模块**，草案里的子模块拆分基本还适用，可以作为
`02-perception.md` 的种子清单：相机采集、相机标定、图像预处理、目标识别、
目标定位、视觉结果滤波/跟踪。草案里还提到的"避障感知模块"、深度相机/
光流/雷达可以**去掉**——竞赛规则里没有提到需要避障，任务是识别静态天井
里的靶标，不是导航避障，属于草案写在具体规则之前、过度设想的部分。

**规划/决策模块**，草案的子模块拆分同样基本适用，可作为 `03-planning.md`
的种子清单：任务状态机、任务流程管理、航点/路径生成、目标选择与确认、
投放/动作决策、飞控通信、安全与异常处理。**值得注意的一点**：草案把
"飞控通信模块"列成规划/决策内部的一个子模块，而不是独立的一个模块——
这是当时作者（可能是你自己或者之前的 AI 会话）的一个倾向性判断，跟本
文档"开放问题 1"（接口层要不要独立成模块）是同一个问题，草案给出的是
"合并"这个答案，可以作为讨论开放问题 1 时的一个参考意见，但不代表已经
拍板。

**数据日志**：草案提出感知结果、规划状态、任务事件、MAVLink 通信、电源/
硬件状态都应该可记录，这个方向依然成立，值得在 `00-index.md` 或单独的
日志文档里提，具体用什么机制（rosbag、自定义日志格式）还没讨论。

**安全与异常处理的横向原则**：草案里明确提出安全处理不需要单独拆成一个
模块，而是分布式的——飞控内部负责 Failsafe（低电、遥控失联、GPS异常等）、
规划/决策模块负责任务逻辑异常（目标丢失、置信度不足、状态机超时）、
通信系统负责链路状态监测、硬件层负责人工安全输入（Arming/Kill switch）。
这个框架依然成立，建议原样带进 `00-index.md` 的横向关注点部分。

**一个草案里没拍板、现在很可能已经被规则事实上决定的开放问题**：草案
第5.3节讨论过"机载计算"（相机图像在伴随计算机上做识别决策）vs"地面站
自动计算"（图像通过图传回地面，地面电脑识别决策，再传回飞控）两条路线，
当时没有下结论。现在我们已经知道自主飞行的规则定义是"侦察和打击阶段
不能操作地面站或上位机"——这不是直接禁止地面站做计算，但让"实时图传+
地面计算+指令回传"这条路线在一个 8 分钟计时、要求全程自主的任务里显得
风险很高（延迟、链路稳定性、且几乎不可能在不"操作"地面站的前提下完成
实时闭环）。这几乎已经把答案锁定成"机载计算"，但**还没有正式确认写死**，
建议在 `00-index.md` 里明确把这条结论写下来、关掉这个开放问题，而不是
继续当成待定项拖着。

**草案里现在明确出局、不用带进新 spec 的部分**：飞控/执行模块本身的实现
（属于飞控组）、地面站调试/可视化系统（除非我们自己需要一个查看识别结果
的工具，那也是我们自己按需设计，不是照搬草案第6节）、电源/供电系统、
机体结构与载荷集成、投放/执行机构的机械设计——这些都是飞控组或结构组的
工作范围。
