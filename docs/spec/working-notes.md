## 已经决定的事

- **范围**：本仓库只覆盖伴随计算机软件（感知/视觉、规划/决策、与
  ArduPilot 的通信接口）。飞控本身（Pixhawk 参数、PID、机体、投放机构）
  由飞控组负责，不在本仓库范围内，只作为外部接口契约引用（见
  `docs/reference/ardupilot-interface-overview.md`）。
- **ROS 版本**：ROS2 Humble（与本机其它项目 `ros_ws` 环境一致，已安装在
  `/opt/ros/humble`）。
- **仓库布局**：仓库根目录本身就是 colcon workspace 根（`src/` 直接在根下，
  不额外嵌套一层），docs/spec 是设计规范、docs/reference 是外部背景资料，
  两者更新的动机不同（spec 因为我们自己设计变了而改，reference 只因为外部
  来源变了或摘录有误才改）。
- **git**：单一仓库（docs 和代码放一起，不拆成两个仓库），因为 spec 变化
  和代码实现紧密相关，希望同一个 commit/PR 里能同时看到两者的对应关系。
- **仿真资产归属**：
  - 我们自己写的仿真场景（比赛场地世界文件、投放区/灾情侦察区的圆筒和
    危险化学品标识模型、spawn 和话题桥接的 launch 文件）属于我们自己的
    代码，是 `src/` 里的一个普通 ROS2 包，包名已定为 `cuadc_sim`（见
    [`src/cuadc_sim/README.md`](../../src/cuadc_sim/README.md)）。
  - **ArduPilot SITL**（ArduPilot 固件自带的软件在环模拟器）和
    **`ardupilot_gazebo`**（连接 SITL 飞行动力学和 Gazebo 物理/传感器的
    桥接插件）、**`ardupilot_gz`**（Gazebo+ROS2 的集成层）都是第三方
    代码，不是我们写的，**不 vendor 进本仓库**，应作为外部依赖单独安装
    （类似 ROS2 Humble 本身不会被塞进任何项目仓库）。安装位置（都不在
    仓库内）：
    - `~/ardupilot`——ArduPilot 源码 + SITL（内置物理模型）
    - `~/ardupilot_run_builtin_physics`——SITL 运行时状态/日志（内置
      物理模型那次）
    - `~/ardupilot_run_gazebo_physics`——SITL 运行时状态/日志（接
      Gazebo 那次）
    - `~/ardupilot_gazebo`——`ardupilot_gazebo` 插件源码+编译产物
      （路径与官方文档一致，不额外套 workspace 外层）
    - `~/gazebo_ros2_ws`——`ardupilot_gz`（ROS2 集成层，已搭建完成，
      本仓库只用它提供的 `ros_gz_bridge`，不使用它自带的 launch 文件）
    - `~/Micro-XRCE-DDS-Gen`——`ardupilot_gz` 编译 SITL 需要的代码生成
      工具，从源码构建
    - `~/QGroundControl.AppImage`——地面站软件
  - 仿真器选型已更新，见下方"已解决"一节——已拍板接入 Gazebo（Harmonic
    版本），推翻了之前"第一阶段只用 SITL"的暂定安排。
- **外部时间约束**：飞控组 phase 1（人工控制下让飞机飞起来，调姿态/悬停
  这些控制环）需要在 **2026-08-01 前**完成。2026-07-17 重新确认过：这
  部分调参跟软件组不互相阻塞——ArduCopter GUIDED 模式复用的是 Stabilize/
  Loiter 这些手动模式底层同一套 `pos_control`/`attitude_control`/
  `wp_nav`，飞控组用遥控器手动飞就能把这些核心控制环调好，不需要伴随
  计算机、不需要知道任务语义或规划/决策模块的具体指令。接口层
  （`04-interfaces.md`）已经把 ROS2 话题翻译成 ArduPilot 认识的标准
  GUIDED MAVLink 协议，飞控组也不需要专门了解这层翻译，两边交界处是
  ArduPilot 自己定义的公开协议，不是私有约定。唯一可能受益于真实 GUIDED
  指令验证的是少数 GUIDED 专属参数（`GUID_TIMEOUT`、`WPNAV_SPEED`/
  `WPNAV_ACCEL` 这类），但验证这些也只需要随便发几个通用指令，不需要
  等规划/决策模块。

## 已解决、迁移进正式文档的问题

接口层的模块边界、技术路线（自研 pymavlink，不用 MAVROS）、话题/服务
契约已经全部迁移进 [`04-interfaces.md`](04-interfaces.md) 和
[ADR-0001](adr/0001-interface-layer-separate-module.md)，本文件不再
重复维护。

- **"机载计算" vs "地面站自动计算"**：已拍板为"机载计算，无地面站计算
  路径"，见 [ADR-0002](adr/0002-onboard-inference-only.md)（决策依据）
  和 `docs/lessons.md` 2026-07-09 条目（此前推理为什么反复横跳过）。
- **仿真到底要搭多真（第一阶段）**：最初拍板先只装 ArduPilot SITL、不接
  Gazebo，已跑通闭环验证（起 SITL → 读遥测 → 解锁/切 GUIDED/起飞/发送
  位置目标，`sitl_smoke_test` 节点）。**后来重新讨论并推翻了这个暂定
  安排**：只有流程走通、没有真实场景/摄像头画面，规划/决策和感知模块
  的代码没法真正验证（算法本身对不对、不是靠流程通不通能测出来的），
  拍板接入 Gazebo（Harmonic 版本）渲染真实 3D 场景。分支
  `feature/gazebo-sim-integration`。
  - 边界说清楚：接 Gazebo 解决的是"感知算法有没有真实图像可以测"，
    解决不了算力瓶颈（要在目标硬件上测）和真实物理扰动（风、传感器
    噪声这些需要额外配置，Gazebo 本身不会自动模拟）。
  - 当前验证进度、还没做的部分，权威版本在
    [`src/cuadc_sim/README.md`](../../src/cuadc_sim/README.md)，不在
    本文件重复维护（避免和 README 变成两个事实来源）。
  - 暂不写 ADR——这条决策本身记在这里已经够用，等真正搭完整套、
    形成稳定架构后再评估要不要正式写成 spec/ADR。
- **规划模块任务如何触发**：竞赛规则原文（见
  `docs/reference/competition-rules-summary.md` 第 5、7 节）明确分两
  个阶段，不是"飞控/伴随计算机一通电就自动起飞"——准备区通电（开启
  飞行器电源、演示安全开关、走完飞行前检查）在先；比赛计时开始后到
  起降点、按下计时器启动开关、"开启飞行器"（螺旋桨开始转）在后。且
  "螺旋桨旋转前未按下计时器启动开关"是硬性判罚项（该轮零分），所以
  通电和起飞之间必须有一个由人控制时机的独立触发步骤，不能靠"检测到
  PreArm 通过"单一条件自动起飞。
  - 拍板的任务状态机（更新 `03-planning.md` 种子清单）：
    `INIT → WAIT_VEHICLE_READY → WAIT_TASK_START → ARM_AND_TAKEOFF →
    NAVIGATE_TO_DROP_ZONE → DETECT_AND_DROP → NAVIGATE_TO_SURVEY_ZONE →
    DETECT_AND_REPORT → RTL_OR_LAND`。`WAIT_VEHICLE_READY`（心跳 +
    EKF/GPS + PreArm 通过，通常准备区阶段就满足）和 `WAIT_TASK_START`
    （等待任务开始物理信号）是两个独立条件，都满足才进入
    `ARM_AND_TAKEOFF`。
  - 拍板三个独立物理开关，职责不重叠、不合并：
    - **总电源开关**：给伴随计算机 + 飞控通电，触发伴随计算机
      systemd 开机自启所有 ROS2 节点，飞控走 PreArm 检查。准备区阶段
      使用。
    - **任务开始开关**：独立于总电源，团队在起降点、按完比赛计时器
      开关之后触发，是 `WAIT_TASK_START` 条件的信号源，触发后状态机
      自动执行到底，不再需要人工介入。
    - **安全开关**（规则硬性要求）：仅用于紧急停止，直接硬件切断
      动力（不经过软件判断，即使伴随计算机死机也能生效），赛前需向
      裁判演示。
    - 不合并总电源和任务开始开关：两者发生的时间和地点不一样（准备
      区通电 vs 起降点触发起飞），合并意味着要么在准备区通电瞬间就
      误触发起飞（违规、危险），要么每次都要在起降点重新断电重上电
      触发（浪费 5 分钟比赛时限、增加二次冷启动失败风险）。
    - 不合并任务开始开关和安全开关：语义相反（启动 vs 切断动力），
      且安全开关按规则应保持纯硬件、软件无关。
  - 部署时序（真机）：伴随计算机必须先于飞控上电（至少先于起飞完成
    systemd 自启 + 节点就绪），因为飞控进入"准备好"状态后起飞完全由
    自动状态机驱动，不存在人工在地面站点击解锁/起飞的空间；具体开机
    自启机制（systemd 服务）部署到真机时再落地，仿真阶段不用管。
  - 暂不写 ADR，跟上面"仿真到底要搭多真"一致的处理方式——等真正开始
    实现 `03-planning.md` 时再评估是否需要正式 ADR。

- **三个物理开关信号各自怎么接**（在"规划模块任务如何触发"那条已定的
  三开关分工基础上，进一步明确信号路径）：
  - **任务开关**：直连伴随计算机 GPIO，软件直接读电平触发
    `WAIT_TASK_START`，不经过飞控、不经过接口层/MAVLink——因为它触发
    的是跑在伴随计算机上的状态机转换，没必要绕一圈经飞控。
  - **物理安全开关**：维持原设计，纯硬件直接切断动力，不接伴随计算机
    也不接飞控软件逻辑，这是它"即使伴随计算机死机也能生效"这个要求的
    必然结果，不是遗漏。
  - **飞控内部硬 Failsafe**（低电、失联、GPS 异常等）：飞控固件自己
    处理，不经过伴随计算机，飞控挂了/失联伴随计算机也能保基本安全。
  - **规划/决策的任务逻辑安全响应**（比如看 Battery Remaining 低于
    阈值主动提前 RTL）：这层确实跑在伴随计算机上，是规划/决策消费
    接口层转发的遥测（Battery、Failsafe State 等）做出的任务级决策，
    跟飞控自己的硬 Failsafe 是两层不冲突的机制。
  - 结论：安全/触发信号是分布式的，不是"都在伴随计算机上"，也不是
    "都走接口层"——四层各管一段，见 `00-index.md`"横向关注点"。

## 早期架构草案里可复用的部分（已按现在的范围重新解读）

机构等现在明确不归我们管的内容）。**不要把原文整份拿来当参考**——下面是
已经按"仅伴随计算机软件"的范围 + 已知的具体比赛规则重新过滤/解读过的
可复用部分，原文本身不需要再迁移或保留第二份。

**感知/视觉模块**，草案里的子模块拆分基本还适用，可以作为
`02-perception.md` 的种子清单：相机采集、相机标定、图像预处理、目标识别、
目标定位、视觉结果滤波/跟踪。草案里还提到的"避障感知模块"、深度相机/
光流/雷达可以**去掉**——竞赛规则里没有提到需要避障，任务是识别静态圆筒
和危险化学品标识，不是导航避障，属于草案写在具体规则之前、过度设想的
部分。

**规划/决策模块**，草案的子模块拆分同样基本适用，可作为 `03-planning.md`
的种子清单：任务状态机、任务流程管理、航点/路径生成、目标选择与确认、
投放/动作决策、安全与异常处理。**值得注意的一点**：草案把"飞控通信
模块"列成规划/决策内部的一个子模块，而不是独立的一个模块——这是当时

走相反方向（接口层独立成模块），见
[ADR-0001](adr/0001-interface-layer-separate-module.md)。

硬件状态都应该可记录，这个方向依然成立，值得在 `00-index.md` 或单独的
日志文档里提，具体用什么机制（rosbag、自定义日志格式）还没讨论。

**安全与异常处理的横向原则**：草案里明确提出安全处理不需要单独拆成一个
模块，而是分布式的——飞控内部负责 Failsafe（低电、遥控失联、GPS异常等）、
规划/决策模块负责任务逻辑异常（目标丢失、置信度不足、状态机超时）、
通信系统负责链路状态监测、硬件层负责人工安全输入（Arming/Kill switch）。
这个框架依然成立，建议原样带进 `00-index.md` 的横向关注点部分。

没有下结论，现已拍板（见上方"已解决、迁移进正式文档的问题"一节和
[ADR-0002](adr/0002-onboard-inference-only.md)）。

机体结构与载荷集成、投放/执行机构的机械设计——这些都是飞控组或结构组的
